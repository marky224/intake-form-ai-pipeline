# Synthea bring-up

Thin Docker wrapper around the upstream Synthea JAR. Generates synthetic FHIR
patient bundles that feed the Phase 3 CMS-1500 rendering pipeline.

## Pinned release

- **Version:** `v4.0.0` (released 2026-03-05)
- **JAR:** `synthea-with-dependencies.jar`
- **SHA-256:** `ed43c20ad40ba5c3bc724503a5af032715fe3c491620b766148e7c2361e6ecc1`

The Dockerfile downloads this exact JAR at build time and verifies the
checksum. Bump `SYNTHEA_VERSION` and `SYNTHEA_JAR_SHA256` in `Dockerfile`
together when upgrading.

## Running

From the repo root:

```bash
just synthetic-data-patients 10          # 10 patients, default seed 42
just synthetic-data-patients 500 1337    # 500 patients, seed 1337
```

Output: `synthetic_data/output/synthea/fhir/*.json` (gitignored). One FHIR
Bundle JSON per patient plus auxiliary `hospitalInformation*.json` and
`practitionerInformation*.json` bundles (Synthea writes these once per run).

## Regenerating the test fixture

The fixture committed at `tests/fixtures/synthea/fhir/` is six trimmed FHIR
bundles. The recipe asks Synthea for `-p 5` patients but Synthea wrote 6
bundles: one patient died mid-simulation and was replaced to keep five
alive at export time. We commit all six.

The Dockerfile sets `--exporter.years_of_history=1` to bound bundle size,
but elderly-patient bundles still run several MB. The committed fixture is
therefore trimmed down to **Patient + 3 most recent Encounters per bundle**
(see `_trim_for_fixture.py`). Trimmed bundles are valid FHIR R4 and
preserve the exact shape the parser cares about.

To regenerate (e.g., after a Synthea version bump):

```bash
just synthetic-data-patients 5 42
uv run python -m synthetic_data.synthea._trim_for_fixture \
    synthetic_data/output/synthea/fhir \
    tests/fixtures/synthea/fhir
uv run pytest test_synthea_parse.py
```

Determinism: same Synthea version + same seed + same state + same
`years_of_history` produces the same set of patient names, demographics,
and encounter dates. UUIDs derive from a separate RNG stream that Synthea
does not seed, so they vary between runs — `test_synthea_parse.py` does
not assert on UUIDs for this reason.

## A note on the fixture's embedded version string

The committed bundles include a narrative `text.div` field that reads
`Version identifier: v3.4.0-18-ga07a65555`. That string is Synthea
v4.0.0's own `git describe` output (the v4.0.0 tag was cut 18 commits
after the v3.4.0 tag), embedded by Synthea itself in every bundle it
generates. It is *not* a stale fixture — all six bundles in the
committed fixture were generated by the pinned v4.0.0 JAR.
